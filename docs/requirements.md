# 需求与决策记录

2026-09-19 从项目讨论整理，只保存结论，不保存原始聊天或账号信息。

## 产品定位

核心动作是“剪藏”：本人主动向微信客服发送或转发内容，由服务保存到自己的定制版 Memos，便于回顾及后续 AI 检索和延伸交流。最初的独立 MD 文件方案调整为 Memos 的 Markdown 正文及附件，不另建长期 MD 副本。不读取其他微信会话。

当前优先个人自用，不建设通用 SaaS。用户允许在排除敏感信息后公开代码；公开不表示承诺适配所有 Memos，也不等于已选择开源许可证。

## 保存行为

- 一条输入对应一篇私有笔记；默认“个人”空间。图片、语音、视频、文件都是笔记加所属附件，不只是附件库中的孤立文件。
- 只保留实际内容，不添加“微信剪藏”标题、来源、转发时间或辅助接口 JSON。聊天记录保留原有标题、说话人、时间、顺序和可取得的嵌套内容。
- 顶层文字中的分类 #tag 转成 Memos 独立标签，正文不重复；历史聊天中的井号保留原文。默认加“微信剪藏”，聊天记录另加“微信聊天记录”，均可配置。单独发送标签不会修改上一篇。
- 文字 URL 按文字，链接卡片按链接；文章只保存返回的标题、摘要、链接，不抓全文。“链接”是类型名称，文章卡片是可能的内容，不用“链接／文章”表示两个独立保证。
- 用户界面统一称“聊天记录”。独立微信笔记因接口不返回正文，不创建 Memos 占位；聊天记录内的不可取内容明确报告部分保存。
- 位置、小程序、视频号、商品及订单只保存官方实际提供的字段。完整矩阵与限制见 message-support.md，不把结构支持等同于真机验收。

## 结果反馈

不发“收到”或“处理中”。完整保存后只回“文字保存成功”“图片保存成功”“聊天记录保存成功”等，不带标题、标签、空间、笔记链接。

最终失败说明类型、实际失败环节、可安全展示的具体原因、状态码和尝试次数；不要求“请稍后重发”。已建笔记但附件失败时说明部分保存。不得把服务令牌、远端响应正文或含密钥 URL 放进回复。

用户新输入后才有回复窗口；48 小时/5 条不是整个客服号每两天只能发五条。额度不视为多个输入可无限累加，具体执行及不确定发送处理见 receipts.md。结果回执不重新触发 Memos 保存。

## 可靠性与存储

SQLite 负责游标、待处理任务、去重、事件和回执状态，不是第二套长期笔记库。成功任务清除原消息正文；失败和未处理任务仍属敏感数据。附件当前只在内存中转运，最终由 Memos 长期保存；素材过期可能影响重试恢复。

本人白名单默认拒绝未授权用户，Memos 仅用 API，维护固定 ID 与事务恢复。只部署一个工作进程。未知内容或部分缺失不能虚报全部成功。

## 暂不做

微信笔记占位、OCR、语音转写、视频号本体下载、文章全文抓取、超长笔记自动拆分、跨消息补标签、桥接内置 AI、网页管理、多租户及服务商代管。代码保留 markdown 标签兼容模式，但当前维护与验收以定制 explicit 模式为主。
